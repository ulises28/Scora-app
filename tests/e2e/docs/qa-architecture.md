# Scora QA Architecture

_Architect-level test strategy for a high-churn sticker product with hard environment constraints._

**Status:** living document · **Date:** 2026-10-12 · **Companion:** `suite-health.md` (operational gate status)

---

## 1. Mission

Ship **trustworthy sticker rendering** (data + pixels) across many templates and activity types, while:

| Constraint | QA implication |
|------------|----------------|
| **Login is not working** | Real OAuth / Strava login is **out of scope**. All app-flow tests run on **injected mock auth**. Auth remains an **open risk**, not a green test. |
| **Stickers change constantly** | Visual baselines must be **lifecycle-managed** (create / accept / archive with the sticker), not a static PNG dump. Exhaustive per-sticker goldens do not scale. |
| **Same sticker, different data by activity** | The **unit of specification is `(sticker × mode)`**, not “sticker.” 36/39 active stickers already differ in metrics across `run` / `bike` / `workout`. |

---

## 2. Product surface under test

```
Strava activity (mock or real)
        │
        ▼
   Activity feed  ──►  Sticker grid  ──►  Editor (story canvas 1080×1920)
                                                │
                                    ┌───────────┼───────────┐
                                    ▼           ▼           ▼
                                 DOM chrome   Canvas paint  Export PNG
                                              (metrics +
                                               materials)
```

**What we can test without login:** everything after mock auth — feed, grid, editor, canvas contracts, export naming, admin reset (where mocked).

**What we cannot test until login works:** real OAuth redirect, token refresh, live Strava API, queue slot lock against production, account switching.

---

## 3. Test pyramid (aligned to constraints)

```
        ┌──────────────────┐
        │  Visual heroes   │  few, stable, reviewed accepts
        │  (golden pixels) │  one OS · fixed set · per mode
        ├──────────────────┤
        │  Display contract│  every sticker × mode: WHAT data paints
        │  (E2E data scan) │  driven by sticker-capabilities.json
        ├──────────────────┤
        │  Unit contracts  │  sync integrity, formatters, glass buffers,
        │                  │  registry ↔ fixture, render smoke
        └──────────────────┘
```

| Layer | Owns | Does **not** own |
|-------|------|------------------|
| **Unit** | Registry ↔ JSON sync, spelling/formatters, buffer budgets, “renders without throw” | Pixel look, DOM navigation |
| **Display contract (E2E)** | For each **(sticker, mode)**: required metrics/labels on canvas text log | Exact typography/color |
| **Visual heroes** | A **small, named** set of critical looks | Exhaustive catalog coverage |

Rationale: catalog churn invalidates pixels often; **data contracts** are cheap and survive redesigns when the JSON is updated with the sticker. Pixels are for the few looks the product cannot afford to silently break (glass numbers, hero layouts).

## 4. Source of truth — display contract

**File:** `tests/e2e/fixtures/sticker-capabilities.json`  
**Schema:** `sticker-display-contract/v1`  
**Generated by:** `pnpm run sync:stickers` (`scripts/sticker-sync.ts`) — **sole writer**.

This file answers: **“On this sticker, in this activity mode, which data is displayed, and how is it painted?”**

```jsonc
"stickers": {
  "<id>": {
    "modes": {
      "run":     { "metrics": [...], "labels": [...], "metadata": [...], "display": {...} },
      "bike":    { ... },
      "workout": { ... }
    }
  }
}
```

### Why `(sticker × mode)` is the unit

Same renderer branches on `hasDistance` / sport. Examples of **contract variance**:

| Sticker | Run (distance) | Workout (no distance) |
|---------|----------------|------------------------|
| `circle-letters` | distance word + hero km | spelled minutes |
| `word-metric` | spelled **kilometers** | spelled **minutes** |
| `glass-numbers-v2` | glass digits = distance | glass digits = duration |
| `studio-precision` | distance + pace + time columns | duration-centric layout |

**36 of 39** active stickers already have different metric sets across modes. A test plan that says “test the sticker” without a mode is incomplete.

### Paint forms (`display.*`)

| Form | Canvas mechanism | Assertion strategy |
|------|------------------|--------------------|
| `numeric` | `fillText` number | needle in text log |
| `spelled` | `fillText` words (`spellNumber`) | spelled needle |
| `segments` | LED bars (not fillText) | paint occurred + visual hero if critical |
| `glyphs` | glass offscreen glyphs | paint occurred + visual hero if critical |

## 5. Visual regression strategy (baseline governance)

**Not** “keep every screenshot forever.” **Yes** to managed baselines.

### 5.1 What gets a golden

Only **hero looks** — named, stable, product-critical:

- One representative per **render family** × **mode** (not per sticker id if they share a family).
- Explicit list in `tests/e2e/fixtures/heroes.json` (Phase 2).
- Example families: glass numbers, map+distance, workout duration, spelled word metric, chrome/metal, LED.

### 5.2 Lifecycle (matches sticker churn)

| Sticker event | Golden action |
|---------------|---------------|
| New sticker | Optional hero promotion → generate baseline via **accept** command (human) |
| Visual redesign | Fail → review diff → **accept** (never silent heal) |
| Archive sticker | **Delete** its goldens in the same PR (audit script flags orphans) |
| Rename id | Rename goldens or delete + regenerate; audit fails on strays |
| Mode-only content change | Data scan catches it; hero only if pixels change |

### 5.3 Platform policy

- **Canonical golden OS: linux** (CI). Local darwin goldens are **not** dual-maintained.
- Local loop: data contracts + smoke **without** goldens; optional local visual for practice, not for CI truth.
- Safari/WebKit: **repro / smoke only** (memory + glass), not golden source.

### 5.4 Acceptance protocol (anti–auto-heal)

```
fail (diff) ──► report (which sticker · mode · project · pixels)
            ──► human reviews image
            ──► pnpm run test:e2e:visual:accept   # explicit
            ──► commit baselines in PR with rationale
```

CI may **propose** an update PR; it must **never** push new PNGs to green itself.

## 6. Environment & auth constraints

### 6.1 Login broken — explicit non-goals

| Area | Status |
|------|--------|
| Real Strava OAuth | **Blocked** — do not write tests that pretend it works |
| Token refresh / expiry | **Blocked** (mock only) |
| Live API regression (`@regression` backend) | Requires Vercel + credentials — **quarantined** to `Regression-API`, not in local practice loop |
| App flows after auth | **In scope** via `MockStravaClient` + `injectMockAuth` |

**Practice rule:** a failing auth test that cannot run is worse than no auth test. Track as **risk R-Auth** in the risk register, not as `test.fixme()`.

### 6.2 Local-first

Everyday practice loop (no Docker, no login):

1. `pnpm run test:unit` — display-contract integrity + logic  
2. `pnpm run test:e2e:smoke` — UI-Core on mock auth  
3. `pnpm run test:e2e:scan` — display-contract paint scan (soft asserts)  

Docker/linux goldens and `Regression-API` are **parity / scheduled**, not the practice loop.

## 7. Risk register (QA)

| ID | Risk | Mitigation |
|----|------|------------|
| **R-Auth** | Login/OAuth untestable | Mock auth for flows; document gap; re-open when login ships |
| **R-Churn** | Sticker redesigns break goldens en masse | Hero-only goldens + lifecycle + accept protocol |
| **R-Mode** | Same sticker, different data per activity | `(sticker × mode)` display contract; scan matrix run/bike/workout |
| **R-Heal** | Auto-update baselines hide regressions | Propose-only healer; ban silent `--update-snapshots` / `fixme` |
| **R-Safari** | Memory / glass cost flake | WebKit for repro only; no Safari goldens |
| **R-DualTruth** | Two generators for capabilities JSON | Single writer `sticker-sync.ts` |

## 8. Coverage model

For each **active** sticker we require:

1. **Contract entry** in the JSON (auto from registry + `paintForm`).  
2. **Data scan pass** in every mode the category exercises (`all`/`distance` → run+bike; `workout` → workout; `map` → bike).  
3. **Hero golden** only if on the hero list.  
4. **Render smoke** in unit harness (no throw).

Coverage metric (practice-friendly):

```
coverage = (# stickers with green data scan in all applicable modes)
           / (# active stickers)
```

Target: **100% data-scan coverage** of active stickers. Hero golden count stays **small and stable** (single digits per mode family), not proportional to catalog size.

---

## 9. Anti-patterns (banned)

- Exhaustive `toHaveScreenshot` for every catalog cell × every project × every OS  
- Silent `--update-snapshots` on any source change  
- `test.fixme()` to force green  
- Hand-editing `sticker-capabilities.json`  
- Asserting a single metric set for all activity modes  
- Claiming “auth tested” while login is broken  
- Dual writers for the display contract

## 10. Operating model

| Role | Responsibility |
|------|----------------|
| **Registry** (`StickerRegistry.ts`) | Product claims: features, `paintForm`, category |
| **Sync** (`sticker-sync.ts`) | Emits display contract |
| **Unit** | Contract integrity (registry ↔ JSON ↔ rules) |
| **E2E data scan** | Paint truth vs contract (soft, full report) |
| **E2E heroes** | Pixel truth for critical looks |
| **Healer** | Classify + propose; human accepts baselines |
| **suite-health.md** | Gate status snapshot |

**Change management:** sticker visual change → update registry/`paintForm` if data changes → `sync:stickers` → unit → scan → (if hero) review accept.

## 11. Roadmap (architecture-driven)

| Phase | Outcome |
|-------|---------|
| **0** Inventory | Known failures classified (done) |
| **1** Display contract | Single JSON truth; data scan green (done) |
| **2** Visual governance | `heroes.json`, lifecycle audit, linux-canonical goldens, accept command |
| **3** Honest healer | CI/qa-agent propose-only; no silent PNG writes |
| **4** Local practice loop | `test:unit` / `test:e2e:smoke` / `test:e2e:scan` without Docker |
| **5** Churn hardening | Unit: no orphan goldens; sync fails on unknown flags; archive checklist |

---

## 12. Definition of done (suite)

- [ ] Every active sticker green on data scan in all applicable modes  
- [ ] Hero goldens: named list, one OS, accept protocol documented and used  
- [ ] Orphan golden audit clean after archive/rename  
- [ ] No automated baseline rewrite without human accept  
- [ ] R-Auth explicitly documented; zero fake login tests  
- [ ] New engineer can run the practice loop from this doc alone
